# 量化压缩
神经网络中的浮点数（FP32/FP16）转换为低位整数（INT8）
**量化公式**：  
INT8_value = round(FP_value / scale) + zero_point  
**反量化公式**：  
FP_value = scale × (INT8_value - zero_point)
**参数说明**：  
- `scale`（浮点数）：缩放因子，定义了INT8的"1"等于多少浮点值
- `zero_point`（整数）：零点偏移，确保浮点0.0能准确映射到INT8范围内







# Graph Mode 图模式

## 核心概念

**Graph Mode（图模式）** 是一种通过 CUDA Graph 来优化 LLM 推理的技术。它将推理过程中的多个 GPU 操作"录制"成一个计算图，避免逐个发送命令的开销，从而显著降低推理延迟。

### 问题背景：为什么需要 Graph Mode？

在传统的推理中，每次模型前向传播都需要：
1. CPU 将大量 CUDA 内核调用命令逐个发送给 GPU
2. GPU 驱动和调度器处理这些命令，产生大量CPU-GPU同步开销
3. 在推理场景下（特别是 Decode 阶段），batch size 很小，单个样本计算很快，但**CPU 提交命令的开销反而成为瓶颈**

CUDA Graph 解决这个问题：将所有操作编译成一张"图"，一次性提交给 GPU，减少 CPU-GPU 之间的往返次数。

**收益**：
- 延迟降低 **10-30%**（特别在小 batch decode 场景）
- 更稳定的性能（减少命令调度抖动）
- 降低 CPU 利用率

---

## 原理详解

### CUDA Graph 的工作机制

```
传统方式：
CPU → [命令1] → GPU → 等待 → [命令2] → GPU → 等待 → ...（多轮往返）

Graph 方式：
CPU → [完整图：命令1 + 命令2 + ... + 同步点] → GPU → 一次执行完（最小化往返）
```

CUDA Graph 包含三个核心概念：
- **Nodes（节点）**：GPU 操作（kernel launch、memcpy）
- **Edges（边）**：节点间的依赖关系
- **Graph instance（图实例）**：编译后可重复执行的图

### 对推理的加速原理

#### 1. **Prefill 阶段**（处理提示词）
- 输入序列长度较长，计算密集，kernel 执行时间长
- CPU 提交命令开销相对较小
- **Graph 加速效果有限** ≈ 5-10%

#### 2. **Decode 阶段**（逐 token 生成）
- 单个 token 计算非常快（毫秒级）
- CPU 提交命令开销相对较大（相对于计算时间）
- **Graph 加速效果显著** ≈ 20-40%（相对延迟改善）

**加速的关键**：减少 CPU-GPU 通信往返，让 GPU 尽量连续执行，避免 GPU 空闲等待 CPU 提交新命令。

## 实现方式（vLLM 为例）

### 第 1 步：Memory 和 KV Cache 初始化

vLLM 在服务启动时进行一次性初始化：

```python
# vLLM 初始化伪代码流程
class LLMEngine:
    def __init__(self, model_name, gpu_memory_utilization=0.9):
        # 1. 计算可用 GPU 显存
        total_gpu_memory = get_gpu_memory()
        allocatable_memory = total_gpu_memory * gpu_memory_utilization
        
        # 2. 分配 KV Cache 内存池
        self.kv_cache_pool = allocate_kv_cache_pool(allocatable_memory)
        
        # 3. 初始化 CUDA Graph 相关结构
        self.graph_cache = {}  # 缓存已捕获的 graph
        self.graph_warmup_config = {
            'buckets': [1, 2, 4, 8, 16, 32, 64],  # batch size buckets
            'seq_lens': [128, 256, 512, 1024]  # sequence length buckets
        }
        
        # 4. 加载模型到 GPU
        self.model = load_model(model_name)
```

**KV Cache 的角色**：
- 存储每个 token 生成过程中的 Key 和 Value
- 在 Decode 阶段被重复访问（每次只追加 1 个新 token 的 KV）
- 通过 PagedAttention 等技术进行高效管理（逻辑块 vs 物理块）

### 第 2 步：Prefill Warm-up（可选但推荐）

Prefill 虽然 Graph 加速效果不大，但提前 capture 仍有好处：

```python
def warmup_prefill_graphs(self):
    """预热 Prefill 阶段的 graph"""
    # 针对常见的提示词长度进行预热
    prefill_seq_lens = [128, 256, 512, 1024]
    batch_size = 1  # Prefill 通常单个请求处理
    
    for seq_len in prefill_seq_lens:
        # 创建虚拟输入
        input_ids = torch.zeros(batch_size, seq_len, dtype=torch.long)
        
        # 第一遍：CUDA graph 录制（capture）
        # - CUDA 驱动记录所有 GPU 操作（kernel launch、memcpy 等）
        # - 建立节点间的依赖关系
        with torch.cuda.graph(stream):
            logits = self.model.prefill_forward(input_ids)
        
        # 存储 graph 供后续使用
        self.graph_cache[f'prefill_{seq_len}'] = stream.graph
```

**Prefill warm-up 的作用**：
1. 避免首次推理请求时的 capture 开销
2. 提前检测 GPU 内存不足等问题
3. 确保 graph 编译正确

### 第 3 步：Graph Warm-up 和 Bucket 机制

这是 **Graph Mode 最关键的部分**。

#### 为什么需要 Bucket？

CUDA Graph 需要 **固定的计算流程和内存布局**。如果每次请求的 batch size 或序列长度都不同，就无法复用 graph。

**解决方案**：将输入按大小分组到不同的 "bucket"（桶），每个 bucket 对应一个预先编译的 graph。

```python
def warmup_decode_graphs(self):
    """预热 Decode 阶段的 graph，这是最耗时的部分"""
    
    # Decode batch size buckets（关键参数）
    # 为什么是这些值？根据实际负载统计得出
    batch_size_buckets = [1, 2, 4, 8, 16, 32, 64]
    
    # Sequence length 在 decode 时基本固定（只有输入长度会变）
    # 但因为 KV cache 会不断增长，有多个长度档位
    seq_len_buckets = [128, 256, 512, 1024]
    
    for batch_size in batch_size_buckets:
        for seq_len in seq_len_buckets:
            self._capture_decode_graph(batch_size, seq_len)
```

#### 为什么设置多个 Bucket？

1. **Batch size 变化**：高峰期 batch 很大，低谷期 batch 很小
   - 不同 batch size 的 kernel 配置不同（thread grid 大小）
   - 单一 graph 无法覆盖所有情况
   
2. **Sequence length 变化**：请求生成到不同长度时
   - 虽然 decode 时每次只处理 1 个新 token，但 KV cache 大小会变
   - 不同的 cache 大小需要不同的内存布局和 kernel 参数

3. **内存碎片和效率**：
   - Graph 必须预先分配固定内存
   - 多个 bucket 使得内存分配更灵活

#### 为什么从小到大 Warm-up？

```python
def _warmup_order_matters():
    """为什么顺序重要？"""
    # 正确做法：从小到大
    batch_sizes = sorted([1, 2, 4, 8, 16, 32, 64])
    
    # 原因：
    # 1. GPU 内存从小的请求开始分配，逐步扩大
    # 2. 避免大请求 graph 占用内存后，小请求无法分配
    # 3. 更快地发现内存不足的问题（早期错误）
    # 4. 分阶段初始化更容易调试
```

### 第 4 步：Capture 过程

Capture 是将计算过程"录制"成 CUDA Graph 的过程。

```python
def _capture_decode_graph(self, batch_size, seq_len):
    """捕获单个 graph（vLLM 的简化版本）"""
    
    # 1. 创建虚拟输入（模拟真实推理数据）
    input_ids = torch.ones(batch_size, 1, dtype=torch.long)  
    # Decode: 每次只处理 1 个新 token，但历史有 seq_len 个 token
    
    # 2. 初始化 KV Cache
    # vLLM 使用 Paged KV Cache，这里的 seq_len 代表已有的历史长度
    kv_cache = self.kv_cache_pool.allocate(
        batch_size=batch_size, 
        seq_len=seq_len
    )
    
    # 3. 开始 CUDA Graph Capture
    # 这一步会录制所有 GPU 操作
    stream = torch.cuda.Stream()
    
    with torch.cuda.graph(stream) as g:
        # 前向计算（所有操作都被记录）
        logits = self.model.forward(
            input_ids=input_ids,
            kv_cache=kv_cache,
            is_graph_mode=True  # 标记为 graph 模式
        )
        # Logits shape: (batch_size, 1, vocab_size)
        # 每个位置只处理最后一个 token 的输出
        
        # Sampling（采样下一个 token）
        next_tokens = torch.multinomial(logits[:, -1, :], 1)
        # Shape: (batch_size, 1)
    
    # 4. 编译 Graph（驱动会优化这个 graph）
    # 这一步 GPU 驱动分析依赖关系并优化执行顺序
    graph_instance = g.instantiate()
    
    # 5. 缓存这个 graph
    cache_key = f'decode_b{batch_size}_s{seq_len}'
    self.graph_cache[cache_key] = graph_instance
    
    print(f"✓ Captured graph: {cache_key}")
```

**Capture 的关键点**：

| 阶段 | 说明 |
|-----|-----|
| **录制（Recording）** | `with torch.cuda.graph() as g:` 内所有操作被记录 |
| **编译（Compilation）** | GPU 驱动优化操作顺序和资源利用 |
| **实例化（Instantiation）** | 生成可重复执行的 graph instance |
| **缓存（Caching）** | 存储以供推理时使用 |

### 第 5 步：推理执行流程

#### Prefill 阶段

```python
def forward_prefill(self, prompt_tokens):
    """处理提示词"""
    batch_size = len(prompt_tokens)
    seq_len = max(len(p) for p in prompt_tokens)  # 最长长度
    
    # 1. 查找或创建对应的 graph
    cache_key = f'prefill_s{seq_len}'
    if cache_key not in self.graph_cache:
        # 如果没有现成的 graph，动态 capture
        self._capture_prefill_graph(seq_len)
    
    # 2. 使用 graph 执行前向计算
    graph_instance = self.graph_cache[cache_key]
    graph_instance.replay()  # ← 一次性执行整个图
    
    # 3. 获取输出
    logits = self.model.output  # 从 GPU memory 读出
    
    # 4. 初始化 KV Cache
    kv_cache = self.kv_cache_pool.allocate(batch_size, seq_len)
    
    return logits, kv_cache
```

#### Decode 阶段

```python
def forward_decode(self, batch_size, existing_kv_cache):
    """逐 token 生成"""
    seq_len = existing_kv_cache.current_length
    
    # 1. 选择合适的 bucket
    batch_bucket = self._find_bucket(batch_size, self.batch_size_buckets)
    seq_bucket = self._find_bucket(seq_len, self.seq_len_buckets)
    
    # 2. 查找对应的 graph
    cache_key = f'decode_b{batch_bucket}_s{seq_bucket}'
    if cache_key not in self.graph_cache:
        self._capture_decode_graph(batch_bucket, seq_bucket)
    
    # 3. 执行 graph（关键！）
    graph_instance = self.graph_cache[cache_key]
    graph_instance.replay()  # ← 整个推理一步完成，避免逐个 kernel launch
    
    # 4. 获取下一个 token
    next_token = self.model.sample_output()
    
    # 5. 更新 KV Cache（追加新 token 的 KV）
    existing_kv_cache.append(next_token)
    
    return next_token
```

**执行对比**：

```
=== 无 Graph Mode ===
Token生成循环：
  for step in range(max_steps):
      logits = model.forward(...)      # 多个 kernel launch（CPU 提交）
      next_token = sample(logits)       # 多个 kernel launch（CPU 提交）
      kv_cache.append(next_token)       # memcpy（CPU 提交）
      # 总的说，CPU 每轮循环提交 ~20-50 个 kernel 调用

=== 使用 Graph Mode ===
Token生成循环：
  for step in range(max_steps):
      graph.replay()  # ← 一次 API 调用，GPU 执行所有操作
      next_token = read_output_from_gpu()
      # CPU 只提交 1 次，GPU 一步完成整个前向 + 采样
```

## 关键概念答疑

### Graph 在推理的哪个阶段？

| 阶段 | Graph 使用 | 加速倍数 | 原因 |
|-----|-----------|--------|------|
| **Prefill** | 可选 | ~5-10% | 计算密集，kernel 执行时间长，CPU 提交开销相对小 |
| **Decode** | 必须 | ~20-40% | 计算很快，CPU 提交开销成为瓶颈 |

### 加速的具体计算过程是什么？

以 Decode 为例，一个 forward pass 包含：

```
1. Attention（Q @ K^T，Q @ V）
   └─ 多个 kernel：torch::ops::aten::matmul
2. MLP（线性层）
   └─ 多个 kernel：torch::ops::aten::addmm
3. LayerNorm
   └─ kernel：torch::ops::aten::layer_norm
4. Sampling
   └─ kernel：aten::multinomial
5. KV Cache 更新
   └─ memcpy 或内核 kernel
```

无 Graph：每个操作都需要 CPU 通过 CUDA 驱动 API 逐个提交
有 Graph：这 5 个操作全部预先编译，一次 API 调用全部执行

**加速原理**：
```
延迟改善 = (原始 CPU 提交开销 × 操作数) / (Graph replay 开销)
        ≈ (0.5ms × 20 ops) / 0.05ms ≈ 200% 相对改善
        ≈ 绝对延迟：2ms → 1.2ms
```

## 性能注意事项

### Graph 什么时候不适用？

| 场景 | 原因 |
|-----|------|
| **动态 shape**（形状不固定） | Graph 需要固定内存布局 |
| **极少量请求** | Capture 开销大于收益 |
| **很大的 batch** | Prefill 阶段计算密集，Graph 收益小 |
| **CPU 端处理复杂** | CPU 逻辑开销仍然存在 |

### 最佳实践

```python
# 推荐配置
graph_config = {
    'enable_graph_mode': True,
    'warmup_batch_sizes': [1, 2, 4, 8, 16, 32],  # 根据实际负载调整
    'warmup_seq_lens': [128, 256, 512, 1024, 2048],
    'max_batch_size': 64,  # 超过这个 batch 不用 graph
    'enable_prefill_graph': False,  # Prefill 收益不大
    'enable_decode_graph': True,    # Decode 是主要场景
}
```

## 总结

Graph Mode 的工作流：

```
1. 服务启动 → Warmup（预热 batch 和序列长度的各种 bucket）
2. Warmup 过程：capture → compile → cache
3. 推理时 → 根据请求特征查找合适的 bucket
4. 执行时 → graph.replay()（一次 API 调用 ≈ 数百个 kernel）
5. 收益 → Decode 阶段延迟降低 20-40%
```

关键点：
- **Bucket 机制**：离散化 batch size 和 seq len，每个组合对应一个预编译 graph
- **Capture 录制**：将 forward pass 的所有 GPU 操作记录为一个图
- **Replay 执行**：一次 API 调用执行整个图，避免 CPU 逐个提交 kernel 的开销
- **最大收益场景**：small batch decode，即 LLM 服务的主要计算阶段
